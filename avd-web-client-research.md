# Azure Virtual Desktop Web Client: Authentication Flow & Automation Wrapper Design

## 1. Executive Summary

The Azure Virtual Desktop (AVD) web client at `windows.microsoft.cloud` (which redirects to `windows.cloud.microsoft`) is a Single Page Application (SPA) that uses Microsoft Entra ID (Azure AD) OAuth2 Authorization Code flow with PKCE for authentication, and RDP-over-WebSocket via the Azure Virtual Desktop Gateway for remote desktop sessions. This document analyzes the full authentication flow, VM session connection mechanics, and proposes a wrapper design for automated login, VM listing, and session persistence.

---

## 2. Authentication Flow

### 2.1 Entry Point

| Property | Value |
|---|---|
| Public URL | `https://windows.microsoft.cloud` |
| Resolves to | `https://windows.cloud.microsoft` |
| SPA framework | React + Redux (persisted with redux-persist) |
| Auth library | MSAL.js v4.12.0 (`x-client-SKU: msal.js.browser`) |

### 2.2 OAuth2 Authorization Code + PKCE Flow

The SPA initiates a redirect-based OAuth2 flow with the following parameters:

```
GET https://login.microsoftonline.com/common/oauth2/v2.0/authorize
  ?client_id=451f2815-40fe-44bb-b8a6-3a2e55cf40c4
  &scope=https://www.wvd.microsoft.com/User.Access openid profile offline_access
  &redirect_uri=https://windows.cloud.microsoft/spa-signin-oidc
  &response_mode=fragment
  &response_type=code
  &code_challenge_method=S256
  &code_challenge=<PKCE_challenge>
  &x-client-SKU=msal.js.browser
  &x-client-VER=4.12.0
  &state=<base64_json>
  &nonce=<random>
  &client_info=1
```

Key observations:
- **client_id `451f2815-40fe-44bb-b8a6-3a2e55cf40c4`** is the Azure Virtual Desktop SPA registration — this is the public client ID.
- **Scope** requires `https://www.wvd.microsoft.com/User.Access` for the feed discovery API, plus standard `openid profile offline_access`.
- **response_mode=fragment** means the auth code comes back in the URL hash fragment (SPA pattern).
- **PKCE** (S256) is enforced — prevents authorization code interception.
- **state** is a base64-encoded JSON: `{"id":"<guid>","meta":{"interactionType":"redirect"}}`.

### 2.3 Login Page Elements

The Microsoft sign-in page at `login.microsoftonline.com` presents:

| Element | Type | Ref | Notes |
|---|---|---|---|
| "Sign in" heading | h1 | @e5 | Main heading |
| Email/phone input | textbox (required) | @e6 | First step of login |
| "Next" button | button | @e8 | Submits email |
| "Sign-in options" | button | @e4 | Alternative auth methods (FIDO2, Windows Hello, etc.) |
| "Can't access your account?" | link | @e7 | Account recovery |
| Terms of use / Privacy | links | @e1, @e2 | Footer links |

Initial cookies set: `AADSSO=NA|NoExtension`, `SSOCOOKIEPULLED=1`, `brcap=0`.

### 2.4 Authentication Steps (User Journey)

1. **Email entry**: User enters email → redirects to tenant-specific or Microsoft account login.
2. **Password entry**: After email validation, password prompt appears.
3. **MFA prompt**: If enabled (common in enterprise tenants):
   - SMS code entry (textbox for 6-digit code)
   - Microsoft Authenticator push notification (polling for approval)
   - Authenticator app TOTP code (6-digit code entry)
   - FIDO2/Windows Hello (via "Sign-in options")
4. **Stay signed in**: Optional "Keep me signed in" prompt (KMSI).
5. **Redirect back**: On success, browser is redirected to `https://windows.cloud.microsoft/spa-signin-oidc#code=<auth_code>&...`
6. **Token exchange**: MSAL.js exchanges the authorization code for tokens via POST to `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/token`.
7. **Token storage**: Tokens stored in browser `localStorage` under MSAL cache keys.

### 2.5 Token Cache Keys (localStorage)

The SPA uses MSAL's cache format:
- `{homeAccountId}-login.windows.net-{tenant}` — account entity
- `{homeAccountId}-login.windows.net-idtoken-{clientId}-{tenant}-` — ID token
- `{homeAccountId}-login.windows.net-accesstoken-{clientId}-{tenant}-<scopes>` — access token
- `{homeAccountId}-login.windows.net-refreshtoken-{clientId}-{tenant}-` — refresh token

### 2.6 CSRF Protection

No traditional CSRF tokens are used. The OAuth2 `state` parameter serves as the CSRF protection:
- State is generated by MSAL.js before redirect
- Validated upon return to ensure the response matches the original request

## 3. Feed Discovery (VM Listing)

### 3.1 API Endpoint

After authentication, the SPA calls the feed discovery API to get the list of available desktops and apps:

```
GET https://rdweb.wvd.microsoft.com/api/arm/feeddiscovery
Authorization: Bearer <access_token>
```

### 3.2 Response

The API returns digitally signed `.rdp` connection files and application icons for every resource the user is provisioned to access. Each resource contains:

- **Workspace information** (name, ID)
- **Desktop/application name and icon**
- **RDP connection configuration** (gateway address, session host target, authentication token)

### 3.3 Architecture Behind Feed Discovery

1. User's device → Azure Traffic Manager → closest AVD web service instance
2. Web service → AVD broker → geographical database (retrieves RDP files + icons)
3. Results returned to client

### 3.4 Dashboard URL

The main dashboard loads at: `https://windows.cloud.microsoft/#/devices`

The SPA also persists UI state in `localStorage` under `redux-persist` keys:
- `persist:up_home` — home page state, first-run experience flags
- `persist:up_apex` — apex/first-run completion flags
- `persist:up_header_bubble` — help bubble dismissal state
- `persist:nativeClient` — native client promotion state

## 4. VM Session Connection (RDP over WebSocket)

### 4.1 How Clicking a VM Opens a Session

When a user clicks a desktop or application in the dashboard:

1. The SPA navigates to: `https://windows.cloud.microsoft/webclient/avd/<guid>`
2. This opens in a **new browser window/tab** (detected via `window.open` or navigation)
3. The new page loads an RDP WebAssembly client
4. The RDP client establishes a **WebSocket connection** to the AVD Gateway

### 4.2 RDP Connection Sequence

1. Client resolves the nearest AVD gateway via Azure Front Door (lowest latency)
2. Client establishes a **secure TLS WebSocket (WSS)** to the gateway
3. Gateway validates the request and asks the AVD broker to orchestrate
4. Broker identifies the session host and instructs its agent to connect to the **same gateway**
5. Gateway begins **relaying RDP traffic** (TCP) between client and session host — this is the "reverse connect transport"
6. RDP handshake occurs over the nested TLS tunnel between client and session host
7. Session is active — display and input flow through the WebSocket relay

### 4.3 Gateway Service

The gateway is a **WebSocket relay service** provided by Microsoft:
- Global entry via Azure Front Door
- ~40 Azure regions with redundant instances
- TLS 1.2 minimum (TLS 1.3 when client + session host support it)

### 4.4 WebSocket Connection Characteristics

- **Transport**: WSS (WebSocket Secure) over TLS
- **Traffic**: RDP protocol data tunneled through WebSocket frames
- **Gateway URL pattern**: Resolved dynamically via Azure Front Door (not a fixed URL)
- **Session URL pattern**: `https://windows.cloud.microsoft/webclient/avd/<guid>`
- **Alternative**: RDP Shortpath (UDP direct to session host, bypassing gateway) — **not available in web client**

### 4.5 Chromium Requirements for RDP

The RDP WebAssembly codec requires specific browser features:

| Feature | Purpose | Flag |
|---|---|---|
| SharedArrayBuffer | Required by RDP WebAssembly codec | `--enable-features=SharedArrayBuffer` |
| CrossOriginOpenerPolicy | Required for SharedArrayBuffer isolation | `--enable-features=CrossOriginOpenerPolicy` |
| VAAPI Video Decode | Hardware H.264 decode for RDP graphics | `--enable-features=VaapiVideoDecoder` |

Without these:
- The RDP graphics stream falls back to CPU decode (high CPU usage)
- SharedArrayBuffer denial = WebAssembly codec won't load = session fails

### 4.6 User-Agent Spoofing Requirement

Many enterprise AVD tenants enforce Conditional Access policies requiring Microsoft Edge on Windows. The web client checks both:

1. **HTTP User-Agent header**: Spoofed at the session/browser level
2. **Client Hints API** (`navigator.userAgentData`): Spoofed via JavaScript preload injection

Spoofed UA example:
```
Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/143.0.0.0 Safari/537.36 Edg/143.0.0.0
```

Spoofed Client Hints:
- `sec-ch-ua`: `"Microsoft Edge";v="143", "Not_A Brand";v="99", "Chromium";v="143"`
- `sec-ch-ua-platform`: `"Windows"`
- `navigator.platform`: `"Win32"`
- `navigator.userAgentData.platform`: `"Windows"`

## 5. Wrapper Design

### 5.1 Tool Selection: Playwright vs Puppeteer vs Electron

| Criterion | Playwright | Puppeteer | Electron |
|---|---|---|---|
| Browser automation API | ✅ Excellent | ✅ Good | ⚠️ Manual (Chromium API) |
| Session persistence | ✅ context.storageState | ✅ cookies/localStorage export | ✅ Native session partition |
| MFA interception | ✅ page.waitForSelector | ✅ page.waitForSelector | ⚠️ Manual IPC |
| Multi-window (AVD sessions) | ✅ BrowserContext | ⚠️ Manual | ✅ setWindowOpenHandler |
| Headless capability | ✅ Yes | ✅ Yes | ❌ GUI required |
| UA spoofing | ✅ Built-in | ✅ Built-in | ⚠️ Manual (HTTP + JS) |
| Wayland support | ✅ | ⚠️ Partial | ⚠️ Manual flags |
| Chromium flag control | ✅ launch args | ✅ launch args | ✅ app.commandLine |
| Language ecosystem | JS/Python/.NET/Java | JS | JS |
| Production deployment | Script/Service | Script/Service | Desktop app |

**Recommendation**: **Playwright** for headless automation, with **Electron** as an alternative for interactive/desktop use cases.

Rationale:
- Playwright has first-class `storageState` persistence for session reuse (avoid re-login)
- Multi-context support allows main dashboard + AVD sessions in separate isolated windows
- Headless mode supports server-side deployment
- Built-in UA spoofing and Chromium flag passing
- Python bindings available (wider ecosystem)

### 5.3 Component Details

#### Auth Module
Handles the OAuth2 login flow:

1. Navigate to `https://windows.cloud.microsoft`
2. Detect redirect to `login.microsoftonline.com`
3. Fill email field, click "Next"
4. Fill password field, click "Sign in"
5. **MFA handling** (see Section 5.4)
6. Wait for redirect back to `windows.cloud.microsoft/spa-signin-oidc`
7. Wait for dashboard to load (`/#/devices`)
8. **Save browser state** (cookies, localStorage) for future sessions
9. Return authenticated page/context

#### Feed Discovery Module
Retrieves available VMs programmatically:

1. Extract access token from MSAL localStorage cache (or intercept the API call)
2. Call `GET https://rdweb.wvd.microsoft.com/api/arm/feeddiscovery` with Bearer token
3. Parse response for available desktops/applications

Alternative: Scrape the dashboard DOM for VM list items.

#### Session Manager
Handles VM connections:

1. For each VM resource, navigate to or open: `https://windows.cloud.microsoft/webclient/avd/<guid>`
2. In Playwright: create a **new page** in the same browser context (shares auth state)
3. Wait for RDP WebSocket connection to establish
4. Monitor session health (page crashes, WebSocket disconnects)
5. Handle reconnection with session state clearing

**Critical detail**: Before reconnecting to an AVD session, clear `indexeddb`, `sessionstorage`, `serviceworkers`, and `cachestorage` (but NOT `localStorage` or `cookies` — these hold auth state and first-run flags). The windows-app-for-linux project documents this as the fix for a "grey screen on reconnect" bug.

### 5.4 MFA Handling Strategy

Three approaches, ordered by reliability:

#### Option A: TOTP Secret Integration (Recommended)

Prerequisites:
- User must configure their Microsoft Authenticator to expose the TOTP secret
- Go to `https://mysignins.microsoft.com/security-info` → Add sign-in method → Authenticator app → "I want to use a different authenticator app" → "Can't scan image?" → copy the secret key
- Set Microsoft Authenticator to use "code" (not push) as default method

Implementation:
```python
import pyotp

def handle_mfa(page, totp_secret):
    # Wait for MFA code input field
    page.wait_for_selector('input[name="otc"]', timeout=30000)
    # Generate TOTP code
    code = pyotp.TOTP(totp_secret).now()
    # Fill and submit
    page.fill('input[name="otc"]', code)
    page.click('input[type="submit"]')
```

Storage: TOTP secret in environment variable or secrets manager (not plaintext in code).

#### Option B: Manual MFA Wait (Simple)

Best for: One-time or infrequent login needs.

1. Automate email + password entry
2. Detect MFA prompt (wait for selector)
3. Pause and prompt the human operator for the code
4. Operator enters code manually via stdin or a simple UI
5. Script continues from there

```python
def handle_mfa_manual(page):
    page.wait_for_selector('input[name="otc"]', timeout=30000)
    print("[MFA] Enter the 6-digit code from your authenticator:")
    code = input().strip()
    page.fill('input[name="otc"]', code)
    page.click('input[type="submit"]')
```

#### Option C: Session Reuse (Best for Long-Running Automation)

1. Perform full login + MFA once with human assistance (or TOTP)
2. Save browser state to disk: `context.storage_state(path="auth.json")`
3. On subsequent runs, load saved state: `browser.new_context(storage_state="auth.json")`
4. Refresh tokens are automatically used by MSAL.js
5. Only re-authenticate when refresh token expires (typically 90 days)

This is the most practical approach for long-running automation — the MFA is a one-time cost.

### 5.5 Session Persistence & Token Refresh

- MSAL.js stores refresh tokens in localStorage
- Access tokens expire in ~1 hour (configurable in Entra ID)
- The SPA automatically uses the refresh token to get new access tokens
- As long as the browser context persists, sessions stay alive
- For long-running automation: periodically navigate to the dashboard to trigger token refresh

### 5.6 Key Implementation Notes

#### Required Chromium Launch Flags
```python
browser = playwright.chromium.launch(
    headless=True,
    args=[
        '--enable-features=SharedArrayBuffer',
        '--enable-features=CrossOriginOpenerPolicy',
        '--enable-features=VaapiVideoDecoder',
    ]

```

#### Page/Context for AVD Sessions
```python
# Main dashboard
dashboard_page = context.new_page()
dashboard_page.goto('https://windows.cloud.microsoft/#/devices')

# AVD session — new page, same context (shares auth)
avd_page = context.new_page()
avd_page.goto('https://windows.cloud.microsoft/webclient/avd/<guid>')
```

#### AVD URL Detection
```javascript
function isAvdUrl(url) {
    try {
        const { hostname, pathname } = new URL(url);
        return hostname === 'windows.cloud.microsoft'
            && pathname.startsWith('/webclient/avd/');
    } catch { return false; }
}
```

#### Pre-Connection State Clearing
Before loading an AVD session page (especially reconnects), clear stale RDP state:
```python
# Don't clear cookies or localStorage — they hold auth state
cdp_session = await page.context.new_cdp_session(page)
await cdp_session.send('Storage.clearDataForOrigin', {
    'origin': 'https://windows.cloud.microsoft',
    'storageTypes': 'indexeddb,service_workers,cache_storage'
})
```

#### Permission Grants
```python
context.grant_permissions(['camera', 'microphone', 'clipboard-read', 'clipboard-write'])
```

### 5.7 Reference Implementation

The [windows-app-for-linux](https://github.com/mariuszkopowski/windows-app-for-linux) project provides a production-grade Electron wrapper with:
- Full UA spoofing (HTTP headers + Client Hints API)
- windowOpenHandler for AVD session URL detection
- Session persistence across restarts
- CSP header stripping for SSO
- Render process crash recovery
- First-run experience skipping via localStorage patching

This is a useful reference for the Electron approach; a Playwright-based approach would be lighter-weight and headless-capable.

## 7. Known Limitations

| Limitation | Details |
|---|---|
| No RDP Shortpath (UDP) | Web client only supports TCP reverse connect via gateway |
| No multi-monitor | Not supported in web client |
| No screen capture protection | Native client feature only |
| Camera redirection unreliable | Web client support is incomplete — works inconsistently |
| Conditional Access may block | Some tenants require real Edge with specific extensions |
| WebSocket disconnects | Gateway instance failure drops connections; reconnection needed |
| Session state corruption | Stale indexeddb/serviceworkers can cause grey screen — must clear before reconnect |

## 8. Implementation Roadmap

### Phase 1: Auth & Session Reuse
- Playwright script that performs full login (email + password + MFA via TOTP or manual)
- Save `storageState` to disk
- Script that loads saved state and opens dashboard
- Verify VM listing loads

### Phase 2: Feed Discovery & VM Launch
- Parse feed discovery API response or scrape dashboard DOM
- Open AVD session in new page (same browser context)
- Detect WebSocket connection establishment
- Basic session health check

### Phase 3: Session Persistence & Monitoring
- Automatic token refresh detection
- Session reconnection on failure
- Heartbeat/keep-alive mechanism
- Graceful shutdown

### Phase 4: Multi-VM & Production Hardening
- Multiple concurrent VM sessions
- Configurable VM selection
- Error recovery and retry logic
- Logging and observability
